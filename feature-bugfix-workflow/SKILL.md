# 機能開発・バグ修正 タスクテンプレート Skill

フルスタックシニアエンジニアとして、**抜け漏れのない手順（タスク）× 完了条件（DoD）× 証跡**で作業を進める。各タスクの根拠は `references/standards-and-papers.md` にある。規格は「考え方の参考」であり、**準拠の証明ではない**（版・本文は原典で確認）。

## 最初に判定する
| 依頼の種類 | 使うテンプレート |
|---|---|
| 新機能・機能追加・仕様変更 | `references/feature-template.md`（F1〜F9） |
| 不具合・障害・想定外の挙動の修正 | `references/bugfix-template.md`（B1〜B7） |
| 「CLAUDE.md に入れたい」「テンプレ化したい」 | `references/claude-md-snippet.md` を土台に、プロジェクトに合わせて調整 |
| 両方（修正の過程で機能追加が必要など） | バグ修正を先に完了し、機能追加は別タスクとして分ける |

## 進め方（共通ルール）
1. **タスク表を先に出す**：該当テンプレートの全タスクを一覧にし、今回「不要」と判断するタスクは**理由つきで**「N/A」にする。黙って飛ばさない。
2. **1タスクずつ**進め、各タスクの終わりに **DoD（完了条件）と証跡**（テスト結果・差分・文書のパス）を示す。
3. 実装系タスクは、`spec-driven-tdd`（Red → Green → Refactor）があれば併用する。**テストを先に書く**。
4. 不明点は推測で埋めず、質問または未決事項にする。仕様にない機能は足さない。
5. 変更は小さく（1コミット＝1目的）。大きい場合は分割を提案する。
6. 実行できない検証は「未実行」と明記し、コマンドと期待結果を残す。実行していないことを「確認済み」と書かない。
7. **承認は人**：設計の確定、マイグレーションの本番適用、リリース可否、品質基準値は人が決める。AIの自己評価を合格根拠にしない（AIは下書きと点検の補助）。
8. 規格・論文を引用するときは、`references/standards-and-papers.md` にあるものだけを使う。**記憶で新しい文献を追加しない**。追加するなら実在を確認してから。

## 品質ゲート（全タスク共通の確認観点）
ISO/IEC 25010 の品質特性で、変更が影響する観点を確認する：機能適合性／性能効率性／互換性／使用性／信頼性／セキュリティ／保守性／移植性（2023年改訂版では安全性なども追加。使用する版を確認）。設計doc（F1）かバグ分析（B1）の時点で「影響する特性」を選び、以降のテストとレビューに引き継ぐ。

## 報告フォーマット
```markdown
## <FEAT-xxx / BUG-xxx> 進捗
| # | タスク | 状態(完了/N/A/未) | 証跡 | メモ |
|---|---|---|---|---|
## 未決事項・リスク
## 人の判断が必要なこと
```

## 注意
- 論文の結果は特定の条件下の報告であり、効果を保証しない。数値基準（秒数・件数・カバレッジ%）は例であり、人がリスクに応じて決める。
- 個人情報・秘密情報・認証情報をテンプレートやログに書かない。
