```markdown
## 開発タスクの進め方
作業開始時に、該当するタスク表を出し、不要なタスクは理由つきで N/A にすること。
各タスクの完了時に「完了条件」と「証跡」を示すこと。仕様にない機能は追加せず、不明点は質問すること。
本番へ影響する操作（マイグレーション適用・リリース）は人の承認後に行うこと。

### 機能開発（FEAT-xxx）
- [ ] F1 設計document作成（要求ID・受入基準・影響する品質特性・決定理由）
- [ ] F2 データベースマイグレーション（up/down・コピーDBで検証・ロールバック手順）
- [ ] F3 モデル・リポジトリ実装
- [ ] F4 ビジネスロジック実装
- [ ] F5 APIエンドポイント実装（契約・互換性・認証認可）
- [ ] F6 ユニットテスト作成（仕様から期待値を導く）
- [ ] F7 結合テスト作成
- [ ] F8 ドキュメント更新（手順を実際に試す）
- [ ] F9 コードレビュー（重大度つき記録。合否は人）
※ F3〜F6 はテスト先行（Red→Green→Refactor）

### バグ修正（BUG-xxx）
- [ ] B1 バグの再現と原因分析（再現手順固定・根本原因・原因分類）
- [ ] B2 回帰テスト作成（修正前に失敗することを確認）
- [ ] B3 修正の実装（最小変更・1原因1修正）
- [ ] B4 修正の検証（再現手順・B2テスト）
- [ ] B5 影響範囲の確認テスト（影響範囲リスト・関連回帰テスト）
- [ ] B6 リリースノート更新（利用者視点）
- [ ] B7 パフォーマンステストの実行（修正前後を同条件で比較）

### 共通ルール
- コミットは1目的。差分は全て読む
- 実行していない検証を「確認済み」と書かない
- 品質基準の数値は人が決める
```
